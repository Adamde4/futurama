# Futurama — тестовий сайт каркасних будинків

Привіт! Це мій навчальний/тестовий проєкт — тренувався верстати сторінку
і розбирався, як задеплоїти статичний сайт на GitHub Pages. Це не сайт
реальної компанії, контакти, ціни й фото тут для прикладу. Якщо десь
щось криво — я ще вчусь, буду радий фідбеку 🙂

---

Односторінковий, повністю статичний сайт компанії каркасних будинків у
форматі товарного каталогу: модельний ряд з цінами, фільтр за площею,
повторювані форми заявки, блок переваг, FAQ-акордеон. Побудований без
фреймворків і без кроку збірки — це навмисне архітектурне рішення, яке
робить деплой на GitHub Pages максимально надійним.

> Це друга версія дизайну. Перша (редакційна/архітектурна) була замінена
> на конверсійно-каталожну за прямим запитом — структура ближча до
> сайтів-каталогів модульних/каркасних будинків: картки моделей з ціною
> і площею, фільтр, кілька форм заявки по сторінці, FAQ. Візуальна
> ідентичність (кольори, шрифти, іконки) — авторська, не є копією
> жодного конкретного сайту.

## Що це за проєкт

- Односторінковий сайт (`index.html`): hero з ключовими цифрами,
  **модельний ряд** (5 карток з фільтром за площею), блок переваг (3
  іконки), дві "лід"-форми (ім'я + телефон) по тексту сторінки, детальний
  розділ переваг каркасної технології, інтерактивний розріз стіни,
  таймлайн будівництва, **FAQ-акордеон** (8 питань), фінальний CTA, повна
  форма звʼязку, footer у форматі мега-меню, **липкий віджет швидкої
  заявки** внизу екрана.
- Дизайн-система: pine-green + copper палітра, Space Grotesk (заголовки)
  + Inter (текст), картки з softshadow-hover, filter-піли, акордеон.
- Ілюстрації — ті самі архітектурні SVG-скетчі з першої версії
  (легко замінюються на реальні фото моделей).
- П'ять робочих форм на сторінці (2 міні-форми, головна форма, липкий
  віджет) — усі йдуть через один спільний обробник у `js/main.js`.

## Чому без React/Next.js

Немає доступу до npm-реєстру в середовищі розробки, і головна жорстка
вимога ТЗ — стовідсоткова надійність на GitHub Pages без build-помилок.
Ванільний HTML/CSS/JS без кроку збірки усуває весь клас проблем, повʼязаних
із base path і static export на Next.js/GitHub Pages.

## Технології

- HTML5 (семантика, ARIA, `<dl>`/`<ol>` де це відповідає змісту)
- CSS3 (custom properties, Grid/Flexbox, `prefers-reduced-motion`)
- Vanilla JavaScript (без залежностей): фільтр карток, FAQ-акордеон,
  `IntersectionObserver` для reveal-анімацій, спільний обробник форм,
  `<object>` + inline `<style>` для інтерактивного розрізу стіни
- Google Fonts: Space Grotesk (заголовки), Inter (текст)
- SVG-ілюстрації (без растрових зображень і зовнішніх бібліотек)

## Як запустити локально

Збірка не потрібна. Достатньо будь-якого статичного сервера, наприклад:

```bash
cd rama-site
python3 -m http.server 8000
# або
npx serve .
```

Відкрити `http://localhost:8000`.

> Відкривати `index.html` подвійним кліком (протокол `file://`) не варто:
> частина браузерів обмежує `fetch`/`<object>` для локальних файлів.
> Через будь-який `http://localhost` сайт працює повністю, включно з
> інтерактивним розрізом стіни.

## Як задеплоїти на GitHub Pages

Є два способи — обидва увімкнені в цьому проєкті.

**Спосіб 1 — GitHub Actions (рекомендовано, вже налаштовано):**

1. Запуште репозиторій у GitHub, гілка `main`.
2. У налаштуваннях репозиторію: **Settings → Pages → Source → GitHub
   Actions**.
3. Файл `.github/workflows/deploy.yml` уже містить робочий pipeline: він
   просто публікує вміст репозиторію як є (без збірки), тому деплой не
   залежить від npm-реєстру чи версій пакетів.
4. Після пушу в `main` перевірте вкладку **Actions** — деплой завершується
   за секунди, посилання на сайт зʼявиться там же і в Settings → Pages.

**Спосіб 2 — деплой з гілки (без Actions):**

1. **Settings → Pages → Source → Deploy from a branch**.
2. Гілка `main`, папка `/ (root)`.
3. Файл `.nojekyll` уже в репозиторії — без нього GitHub Pages може
   ігнорувати файли/папки, що починаються з `_`.

### Про шляхи

Усі посилання на CSS/JS/зображення в `index.html` та `404.html` — **відносні**
(`css/styles.css`, `images/...`), без провідного слеша. Це критично: коли
сайт опубліковано за адресою на кшталт
`https://username.github.io/rama-site/` (тобто в підпапці, а не в корені
домену), абсолютні шляхи (`/css/styles.css`) вели б повз реальну адресу і
ламали б CSS/JS/картинки. Відносні шляхи працюють коректно незалежно від
того, чи сайт лежить у корені домену, чи в підпапці репозиторію.

Перед публікацією замініть `https://example.github.io/rama-site/` на
реальну адресу вашого сайту у трьох місцях: `<link rel="canonical">` та
`og:url`/`og:image` у `index.html`, і `sitemap.xml`/`robots.txt`.

## Де що змінювати

**Контактні дані** — телефон, email, адреса, Instagram:
- `index.html`: секція `<section class="contact">` та `<footer>`
- `js/main.js`: константа `CONFIG.contactEmail` (використовується для
  форми, якщо бекенд ще не підключено)

**Форма звʼязку (реальний бекенд):**
- `js/main.js` → `CONFIG.formEndpoint`. Впишіть туди URL сервісу типу
  Formspree/Getform або власного API-ендпоінта, що приймає `POST` з JSON.
  Це підключить **усі** форми на сторінці одразу (головну форму, обидві
  міні-форми та липкий віджет), бо всі вони йдуть через один спільний
  обробник `submitLead()`. Поки поле порожнє, кожна форма при відправці
  відкриває поштовий клієнт відвідувача із заповненим листом.

**Ціни та моделі каталогу:**
- `index.html`, секція `id="models"` → `<div class="model-grid">`. Кожна
  `<article class="model-card">` містить назву, площу/кімнати/термін і
  ціну (`<strong>$52 400</strong>`). Атрибут `data-size` (`small` /
  `medium` / `large`) керує фільтром — узгоджуйте його з реальною площею
  при зміні значень.
- Ті самі назви моделей продубльовані у `<select id="fType">` (форма
  внизу) і у footer — онови всі три місця разом.

**Фотографії моделей:**
- `images/project-01.jpg` … `project-05.jpg` — фото моделей Сосна,
  Смерека, Барн, Кедр, Обрій, оптимізовані під веб (JPEG, до 1400px по
  довшій стороні). **Перед публічним запуском переконайтесь, що на ці
  фото є права на комерційне використання** — якщо вони походять із
  Pinterest чи інших чужих джерел без ліцензії, замініть на власну
  фотозйомку об'єктів компанії або ліцензійні стокові фото (Unsplash з
  дозволом на комерційне використання, Shutterstock, Adobe Stock тощо).
- Щоб замінити фото моделі: покладіть новий файл у `images/` (можна під
  тією ж назвою, щоб не міняти код) і онови `src`/`alt` у відповідному
  `<article class="model-card">` в `index.html`, секція `id="models"`.
- Так само `images/hero-house.svg` (hero) та `images/cta-house.svg`
  (фінальний CTA) — це авторські SVG-ілюстрації; замінюються так само
  просто на реальні фото за бажанням.

**Розріз стіни (секція «Технологія»):**
- `images/wall-section.svg` — авторська 6-шарова ілюстрація (штукатурка →
  утеплення → обшивка → каркас з ватою → пароізоляція → оздоблення).
- Текстові описи шарів — в `index.html`, секція `id="technology"`, блоки
  `<div class="wall-layer-info" data-layer="...">`.
- Порядок і назви шарів синхронізовані в трьох місцях: `id="layer-..."`
  групи в SVG, масив `layerIds`/`layerLabels` у `js/main.js`, і
  `data-layer="..."` в HTML. Якщо змінюєте кількість чи назви шарів —
  оновіть усі три місця однаково.

**Тексти (заголовки, описи, переваги, таймлайн):**
- Весь текст живе прямо в `index.html` як звичайний HTML-контент —
  жодних CMS чи JSON-файлів, шукайте потрібний розділ за коментарями
  `<!-- 1. HERO -->` … `<!-- 11. FOOTER -->`.

**Кольори й типографіка:**
- `css/styles.css`, блок `:root` на самому початку файлу — усі кольори й
  шрифти визначені як CSS custom properties.

## SEO та доступність

- Семантичний HTML: один `<h1>` у hero, послідовна ієрархія `<h2>`/`<h3>`
  по секціях, `<nav>`, `<main>`, `<footer>`, `<dl>` для фактів проєктів.
- `title`, `meta description`, Open Graph, `twitter:card`, `canonical`,
  favicon (SVG), `robots.txt`, `sitemap.xml`.
- Усі `<img>` мають змістовний `alt` (декоративні — `alt=""` + `aria-hidden`
  на контейнері).
- Форма: кожне поле має повʼязаний `<label for>`, помилки виводяться в
  `role="alert"`, статус відправки — в `aria-live="polite"`.
- Клавіатурна навігація: видимий `:focus-visible`, `skip-link` на початку
  сторінки, mobile-меню керується `Escape` і `aria-expanded`.
- `prefers-reduced-motion: reduce` вимикає reveal-анімації, паралакс і
  автопрокрутку лічильників — контент одразу видимий.

## Відомі обмеження

- Ілюстрації — авторські SVG-скетчі, а не фотографії. Це свідомий вибір
  (уникнути неякісних/неліцензійних зображень), але перед реальним запуском
  варто замінити їх на професійну фотозйомку об'єктів компанії — інструкція
  вище, у розділі «Де що змінювати».
- Форма без вписаного `CONFIG.formEndpoint` працює через `mailto:` —
  функціонально робоче рішення, але для продакшена рекомендується
  підключити реальний сервіс прийому форм.
- Живий рендеринг у браузері та фактичний GitHub Pages деплой не були
  перевірені мною безпосередньо (див. таблицю QA вище) — рекомендую
  пройти ручний чек-лист після першого пушу.
